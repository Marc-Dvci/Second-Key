Second Key: app map

A take-home guide to where things live. Snapshot of commit ab066b8; the code may have moved on since.

What the app is

A web page that runs on two phones. The parent asks before paying someone new; the second key calls back and reads a six-digit release code. The code is computed on both phones from a secret shared at pairing and the exact request, so only the second key can produce it, and only for that request. Everything a phone knows sits in its own browser storage.

Main pieces
  • src/main.ts: reads the URL, handles incoming pairing and request links, picks the screen.
  • src/core/: the release code, the links, the request model, the scam script table.
  • src/state/storage.ts: each phone's saved pairing and requests.
  • src/ui/views/: one file per screen.

One action, end to end: the parent types the code

Reference route

A reference route through real code, to follow in your editor.

  1. src/ui/views/wait.ts, search const check = async. Reads the six digits, asks for the expected code, and either saves the request as approved or spends one of the three attempts. At zero attempts the request becomes locked.
  2. src/core/code.ts, search export async function releaseCode. HMAC-SHA-256 over canonical(request) with the pairing secret, then truncate() to six digits (RFC 4226 dynamic truncation). The same function runs on the second key's phone to show the code.
  3. src/ui/views/home.ts, search export function renderDone. Shows the turned key only for a request whose saved status is approved.

A practice to reuse

Write the attack as an acceptance criterion, then as a test. The PRD says “changing any field of the request makes its code invalid” (prd.md > Releasing the Code). Turning that into the browser test in tests/e2e/journey.spec.ts (“a code made for a tampered link does not unlock the real request”) showed that the second key's phone ignored a changed copy of a request it had already saved. The fix is the check in src/main.ts, search canonical(known), which refuses the changed copy outright.

On another project: for each thing a user must not be able to do, write the observable result in the requirements and drive it in a test before calling the feature done.
